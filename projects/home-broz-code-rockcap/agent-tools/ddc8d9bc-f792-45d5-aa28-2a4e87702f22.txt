-## Tick-level schema guide
-- Set `OHLC_SCHEMA` to the schemas below when you need tick or book-level data instead of bars.

-
-| Schema | Returned data | When to pick it |
-| --- | --- | --- |
-| `trades` | Every executed trade (time & sales / last sale / tick data). No quotes, just prints. | Use when you only need executions for T&S views, VWAPs, or replaying prints without the book context. |
-| `tbbo` | Each trade, plus the best bid/offer snapshot immediately before that trade’s effect (trade-space top-of-book). | Use when you want to stitch prints with the prevailing BBO without ingesting every quote update. |
-| `mbp-1` | Every top-of-book change (bid/ask price or size) plus the trades that mutate the book (a full L1 book-update feed). | Use for best-effort depth reconstruction, quote imbalance analytics, or anything needing continuous BBO updates. |

-## Overview: What is "State" in React? {#overview}
-
-**State** is data that can change over time and causes the UI to re-render when it changes.
-
-### In Vue (what you know):
-```javascript
-data() {
-  return {
-    activeDate: null,
-    entryPrice: null,
-  }
-}
-```
-
-### In React (what you have):
-```typescript
-const [activeDate, setActiveDate] = useState<string | null>(null);
-const [entryPrice, setEntryPrice] = useState<number | null>(null);
-```
-
-**Key difference:** React splits each piece of state into two parts:
-1. **The value** (`activeDate`)
-2. **The setter function** (`setActiveDate`)
-
-To update state, you **must** call the setter:
-```typescript
-// ❌ Wrong (doesn't work in React)
-activeDate = "2025-10-29";
-
-// ✅ Correct
-setActiveDate("2025-10-29");
-```

-## Computed Values (Derived State) {#computed-values}
-
-**Computed values** are calculated from state but don't need their own `useState`. They recalculate automatically when dependencies change.
-
-### Using useMemo (Cached Computed)
-
-```typescript
-const preset = useMemo(() => 
-  PRESETS.find((p) => p.key === presetKey) ?? PRESETS[0], 
-  [presetKey]
-);
-```
-
-**What this means:**
-- `preset` is a **computed value** (like Vue's `computed()`)
-- It finds the preset object matching `presetKey`
-- It only recalculates when `presetKey` changes (the `[presetKey]` dependency array)
-- React caches the result for performance
-
-**Vue equivalent:**
-```javascript
-computed: {
-  preset() {
-    return PRESETS.find(p => p.key === this.presetKey) || PRESETS[0];
-  }
-}
-```
-
-### Simple Derived Values (No Caching)
-
-```typescript
-const dayData = getDay(activeDate ?? "");
-const candles = dayData?.candles ?? [];
-const trades = dayData?.trades ?? [];
-const startPrice = dayData?.startPrice ?? trades[0]?.price ?? candles[0]?.open ?? null;
-```
-
-**What this means:**
-- These recalculate on **every render** (no caching)
-- They're just JavaScript variables derived from other values
-- `??` is the nullish coalescing operator (like `||` but only for null/undefined)
-- `?.` is optional chaining (safely access properties that might not exist)
-
-**Vue equivalent:**
-```javascript
-computed: {
-  dayData() {
-    return this.getDay(this.activeDate || "");
-  },
-  candles() {
-    return this.dayData?.candles ?? [];
-  }
-}
-```
-
-### Price Calculations (Business Logic)
-
-```typescript
-const longTrigger = startPrice != null ? startPrice + preset.triggerPts : null;
-const shortTrigger = startPrice != null ? startPrice - preset.triggerPts : null;
-const tpPrice = entryPrice != null 
-  ? (direction === "long" ? entryPrice + preset.profitTargetPts : entryPrice - preset.profitTargetPts) 
-  : null;
-const slPrice = entryPrice != null 
-  ? (direction === "long" ? entryPrice - preset.stopLossPts : entryPrice + preset.stopLossPts) 
-  : null;
-```
-
-**What this means:**
-- These are **computed prices** for chart lines
-- `longTrigger`: Start price + trigger points (entry signal for long)
-- `shortTrigger`: Start price - trigger points (entry signal for short)
-- `tpPrice`: Take profit price (above entry for long, below for short)
-- `slPrice`: Stop loss price (below entry for long, above for short)
-- All use ternary operators: `condition ? valueIfTrue : valueIfFalse`

-## Custom Hook: useDayCache {#custom-hook}
-
-This is your only custom hook (like a Vue composable):
-
-```typescript
-function useDayCache() {
-  const cacheRef = useRef<Map<string, DayData>>(new Map());
-  const [, setVersion] = useState(0);
-
-  const setDay = (key: string, value: DayData) => {
-    cacheRef.current.set(key, value);
-    setVersion((v) => v + 1);
-  };
-
-  const getDay = (key: string | null) => {
-    if (!key) return undefined;
-    return cacheRef.current.get(key);
-  };
-
-  return { getDay, setDay } as const;
-}
-```
-
-**What it does:**
-1. Creates a `Map` to cache day data (keyed by date string)
-2. Uses a `useRef` so the Map persists across re-renders
-3. Uses a dummy `useState` to force re-renders when cache updates
-4. Returns `getDay` and `setDay` functions
-
-**Why this pattern?**
-- We want to cache data without re-fetching
-- We want the cache to persist (not reset on re-render)
-- We want components to re-render when cache updates
-- A `Map` is more efficient than an object for this use case
-
-**Vue equivalent:**
-```javascript
-// In Pinia store
-state: () => ({
-  dayCache: new Map()
-}),
-actions: {
-  setDay(key, value) {
-    this.dayCache.set(key, value);
-  },
-  getDay(key) {
-    return this.dayCache.get(key);
-  }
-}
-```

-## Easy Peasy Strategy - Complete Reference
-
-### Overview
-
-The Easy Peasy strategy generates **exactly ONE trade per day** with **two table rows** (Open + Close). The direction (long or short) is determined by whichever trigger price is crossed first.
-
-### Strategy Parameters (from Preset)
-
-| Parameter | Default (PT30) | Description |
-|-----------|----------------|-------------|
-| `triggerPts` | 5 | Points above/below start price to trigger entry |
-| `profitTargetPts` | 30 | Points from entry to take profit |
-| `stopLossPts` | 6 | Points from entry to stop loss |
-
-### Algorithm Flow (7 Steps)
-
-```
-┌─────────────────────────────────────────────────────────────────────────────┐
-│                     EASY PEASY ALGORITHM - 7 STEPS                          │
-├─────────────────────────────────────────────────────────────────────────────┤
-│                                                                             │
-│  STEP 1: Calculate Triggers                                                 │
-│  ─────────────────────────────────────────────────────────────────────────  │
-│  • Long Trigger  = startPrice + triggerPts                                  │
-│  • Short Trigger = startPrice - triggerPts                                  │
-│                                                                             │
-│  STEP 2: Scan for First Trigger Crossing                                    │
-│  ─────────────────────────────────────────────────────────────────────────  │
-│  For each candle in order:                                                  │
-│  • If candle HIGH >= longTrigger  → Long triggered                          │
-│  • If candle LOW  <= shortTrigger → Short triggered                         │
-│  • FIRST trigger hit determines direction                                   │
-│  • If BOTH hit same candle: tiebreaker based on distance from open          │
-│                                                                             │
-│  STEP 3: Calculate Entry Price (WORST-CASE FILL)                            │
-│  ─────────────────────────────────────────────────────────────────────────  │
-│  • Long entry  = candle HIGH (worst price you'd buy at)                     │
-│  • Short entry = candle LOW  (worst price you'd sell at)                    │
-│                                                                             │
-│  STEP 4: Calculate TP and SL from Entry                                     │
-│  ─────────────────────────────────────────────────────────────────────────  │
-│  Long:  TP = entry + profitTargetPts, SL = entry - stopLossPts              │
-│  Short: TP = entry - profitTargetPts, SL = entry + stopLossPts              │
-│                                                                             │
-│  STEP 5: Scan for Exit (TP/SL/EOD)                                          │
-│  ─────────────────────────────────────────────────────────────────────────  │
-│  Starting from candle AFTER entry, scan for:                                │
-│  Long:  TP hit if HIGH >= tpPrice, SL hit if LOW <= slPrice                 │
-│  Short: TP hit if LOW <= tpPrice, SL hit if HIGH >= slPrice                 │
-│  • If BOTH hit same candle → SL wins (conservative)                         │
-│  • If neither by EOD → close at last candle's close price (PUSH)            │
-│                                                                             │
-│  STEP 6: Calculate Exit Price (REALISTIC SLIPPAGE)                          │
-│  ─────────────────────────────────────────────────────────────────────────  │
-│  Exit uses ACTUAL candle price, not theoretical TP/SL:                      │
-│  • Long TP hit  → Exit at candle HIGH (price went higher, better fill)      │
-│  • Long SL hit  → Exit at candle LOW  (price went lower, worse fill)        │
-│  • Short TP hit → Exit at candle LOW  (price went lower, better fill)       │
-│  • Short SL hit → Exit at candle HIGH (price went higher, worse fill)       │
-│                                                                             │
-│  STEP 7: Build Result Rows                                                  │
-│  ─────────────────────────────────────────────────────────────────────────  │
-│  Open row:  { timestamp, type: "Open Long/Short", price: entry }            │
-│  Close row: { timestamp, type: "Close Long/Short", price: exit,             │
-│               note: "PT Hit/SL Hit/EOD Push", net: profit/loss }            │
-│                                                                             │
-└─────────────────────────────────────────────────────────────────────────────┘
-```
-

-### Why Worst-Case Entry / Realistic Exit?
-
-**Entry (Worst-Case):**
-- When you place a market order at the trigger, you don't get the trigger price
-- You get filled somewhere in that candle's range
-- Worst-case assumes you got the worst possible fill in that candle
-- Long: filled at HIGH (you buy at the worst/highest price)
-- Short: filled at LOW (you sell at the worst/lowest price)
-
-**Exit (Realistic Slippage):**
-- If price gaps through your stop, you don't exit at exactly your stop
-- You exit at the actual price the market gives you
-- For losing trades: shows realistic slippage (losses may exceed SL)
-- For winning trades: shows price exceeding TP (profits may exceed target)

-## Backtester Algorithmic Trade Proposals
-
-**User Story:** As a user, I can view a given day's page and see the trades that would have occurred if a strategy was implemented.
-
-### Strategy: "Easy Peasy"
-
-#### Trigger Condition
-- When a candle's price range (high to low) crosses the trigger price, propose a trade
-
-#### Trade Outcome Scenarios
-
-**1. Profit Exit (Win)**
-- Entry: Triggered price (worst-case: candle high for buys, candle low for sells)
-- Exit: Take profit price
-- Result: Positive P&L
-
-**2. Stop Loss Exit (Loss)**
-- Entry: Triggered price
-- Exit: Stop loss price
-- Result: Negative P&L
-

-# Algorithmic Trades - Easy Peasy Strategy
-
-The Algorithmic Trades table shows you exactly what trades the Easy Peasy strategy would have executed for any given trading day.
-
-## What You'll See
-
-When you load a day in the backtester, the Algorithmic Trades table automatically populates with **two rows**:
-
-| Timestamp (ET) | Type | Price | Note | Net |
-|----------------|------|-------|------|-----|
-| 09:06:17 | Open Short | 25291.00 | — | — |
-| 09:06:39 | Close Short | 25300.75 | SL Hit | -9.75 |
-
-- **Open row**: When and where the position was entered
-- **Close row**: When and where the position was exited, plus the result
-
-## How the Strategy Works
-
-### 1. Direction Decision
-
-The strategy determines direction based on **whichever trigger is hit first**:
-
-- **Long Trigger** = Start Price + 5 points
-- **Short Trigger** = Start Price - 5 points
-
-If price goes UP to the long trigger first → **Long trade**  
-If price goes DOWN to the short trigger first → **Short trade**
-
-### 2. Entry Price (Worst-Case)
-
-The entry price assumes you got the **worst possible fill** in the trigger candle:
-
-- **Long entry** = Candle HIGH (you bought at the worst/highest price)
-- **Short entry** = Candle LOW (you sold at the worst/lowest price)
-
-### 3. Take Profit and Stop Loss
-
-From your entry price:
-
-- **Take Profit (TP)** = Entry ± 30 points (depending on direction)
-- **Stop Loss (SL)** = Entry ± 6 points (depending on direction)
-
-### 4. Exit (Realistic Slippage)
-
-When TP or SL is hit, the exit price uses the **actual candle price**, not the theoretical TP/SL level. This accounts for slippage:
-
-- If SL is hit, you might exit at a worse price than your stop
-- If TP is hit, you might exit at a better price than your target
-
-### 5. End of Day (EOD Push)
-
-If neither TP nor SL is hit by market close, the position closes at the last price. This results in a "Push" (could be profit or loss depending on where price ended).
-
-## Chart Lines
-
-The chart shows horizontal lines for the trade:
-
-| Line | Color | What it shows |
-|------|-------|---------------|
-| **Open** | Yellow (solid) | Your entry price |
-| **Close** | Light Yellow (dashed) | Your exit price |
-| **TP** | Green | Take profit level |
-| **SL** | Red | Stop loss level |
-
-Toggle any line on/off using the checkboxes under "Line visibility".
-
-## Reading the Results
-
-**Note column meanings:**
-- `PT Hit` = Take profit was reached (WIN)
-- `SL Hit` = Stop loss was triggered (LOSS)
-- `EOD Push` = End of day close (could be + or -)
-
-**Net column:**
-- Positive = Profit (you made money)
-- Negative = Loss (you lost money)
-
-## Tips
-
-1. **Compare days**: Navigate between days to see how the strategy performs in different market conditions
-2. **Try different presets**: Change the preset (PT30/PT25/PT20) to see how different risk/reward affects results
-3. **Watch the triggers**: The Long TRG and Short TRG lines show you where the entry triggers are

-## Multiple Round Trips
-
-By default, the strategy executes **one trade per day**. You can increase this using the **Max Trades** dropdown (options: 1, 2, 3, or 5).
-
-### How Multi Round-Trip Works
-
-For a 2nd (or subsequent) trade to trigger, **all of the following must be true**:
-
-#### 1. Previous Trade Must Close First
-The prior trade must fully close (TP Hit, SL Hit, or EOD Push). No overlapping positions—never 2 opens at once.
-
-#### 2. Re-Eligibility: Price Must Return Between Triggers
-After a trade closes, price must **return to the zone between the trigger lines** before a new trade can start.
-
-- **Re-eligibility zone**: `Short Trigger < Price < Long Trigger`
-- Example: If a Long trade closes at TP (price is above Long Trigger), price must come back **below** the Long Trigger before any new trade
-
-#### 3. No Same-Candle Re-Entry
-A new trade can only trigger on a **subsequent candle** after re-eligibility. You cannot exit and re-enter on the same candle.
-
-#### 4. Triggers Use Original Start Price
-All trades throughout the day use the **same trigger levels** calculated from the day's start price. Triggers do NOT reset based on exit price.
-
-#### 5. Direction Is Independent
-The 2nd trade can be Long or Short regardless of what the 1st trade was. Whichever trigger is crossed first determines direction.
-
-### Example Multi-RT Flow
-
-1. **Start price** = 25000, Triggers at ±5 pts → Long @ 25005, Short @ 24995
-2. **Trade 1**: Price crosses 25005 → Open Long @ 25006
-3. **Trade 1**: TP hit → Close Long @ 25029
-4. Price returns below 25005 (back into zone) ✅ **Re-eligible**
-5. **Trade 2**: Price crosses 24995 → Open Short @ 24994
-6. ...continues up to max round trips
-
-### RT# Column
-
-When Max Trades > 1, the table shows an **RT#** column indicating which round trip each row belongs to:
-
-| RT# | Timestamp (ET) | Type | Price | Note | Net |
-|-----|----------------|------|-------|------|-----|
-| 1 | 09:06:17 | Open Long | 25006.00 | — | — |
-| 1 | 09:08:45 | Close Long | 25029.00 | PT Hit | 23.00 |
-| 2 | 09:15:22 | Open Short | 24994.00 | — | — |
-| 2 | 09:18:03 | Close Short | 24965.00 | PT Hit | 29.00 |
-
-The **Day Total** in the footer sums the net from all round trips.
-
-## EOD Push (End of Day)
-
-If a trade opens but neither TP nor SL is hit before market close:
-
-- Position closes at the **entry price** (flat exit)
-- Net = **0** (no profit, no loss)
-- Note = **"EOD Push"**
-
-This ensures no positions are held overnight—every open always has a matching close.
-
-## No Trade Days
-
-Some days you may see "No trade generated (trigger not crossed)" - this means price never moved far enough from the start price to trigger an entry. The strategy sat out that day.

-# Understanding `mbp_1` Depth-of-Market Data
-
-This guide demystifies Databento's `mbp_1` (market-by-price, level-1) schema using the sample file at `data/realdatasample.csv`. It assumes no prior knowledge of market data so you can read any row in the CSV with confidence.
-
-## 1. What kind of data is this?
-
-- **Depth of Market (DOM)** captures every change to the top of the order book. Instead of summarizing trading into candles, it streams each add, cancel, and trade that touches the best bid/ask.
-- **`mbp_1` schema** is Databento’s compact format for level-1 prices: after every event you get the resulting best bid/ask prices, sizes, and order counts.
-- **Use cases:** tracking liquidity shifts, identifying when trades consume the bid/ask, building microstructure analytics, or replaying the order book tick-by-tick.
-
-## 2. What is a “row”?
-
-Each row is one feed message from the CME Globex MDP3 feed (`GLBX.MDP3`). The row includes:
-
-1. **Event metadata** – when it happened (`ts_event`), who published it (`publisher_id`), ordering (`sequence`).
-2. **Action details** – e.g., add (`A`), cancel (`C`), trade (`T`), and whether it impacted the bid or ask.
-3. **Resulting top-of-book snapshot** – `bid_px_00`, `ask_px_00`, and their sizes/counts right after the action.
-
-So, a row answers “what just happened?” and “what does the best bid/ask look like now?”.
-
-### Example row
-
-```
-1:3:data/realdatasample.csv
-ts_event,rtype,publisher_id,instrument_id,action,side,depth,price,size,flags,ts_in_delta,sequence,bid_px_00,ask_px_00,bid_sz_00,ask_sz_00,bid_ct_00,ask_ct_00,symbol,date
-2025-08-29 13:29:59.999832391+00:00,1,1,42008487,T,A,0,23652.0,4,0,12916,194342358,23652.0,23652.5,4,5,3,5,NQU5,2025-08-29
-```
-
-- A trade (`action=T`) hit the ask (`side=A`) for 4 contracts at 23,652.
-- After the trade, the best bid remains 23,652.00 with 4 contracts, best ask 23,652.50 with 5.
-
-## 3. Column-by-column breakdown
-
-| Column | Type | What it represents | Why it matters |
-| --- | --- | --- | --- |
-| `ts_event` | Timestamp (UTC, nanosecond precision) | Exchange timestamp when the event occurred. | Rebuild sequences in time order and measure latencies. |
-| `rtype` | Small int (always `1` here) | Record type identifier (Level-1 MBP). | Guards against mixing incompatible schemas. |
-| `publisher_id` | Int | Feed publisher ID (venue). | Distinguishes multiple venues if you aggregate feeds. |
-| `instrument_id` | Int | Databento’s numeric instrument key. | Unique instrument reference regardless of event text. |
-| `action` | Char (`A`,`C`,`T`,`M`) | Operation: Add, Cancel/Change, Trade, or Marker. | Tells whether liquidity was added, removed, or traded. |
-| `side` | Char (`B`,`A`,`N`) | Which side the action applied to (Bid, Ask, Neutral). | Combined with `action` to interpret the effect. |
-| `depth` | Int (0) | Price level index (0 = best bid/ask). | Higher depths appear in `mbp_10`; here it’s always top-of-book. |
-| `price` | Decimal | Price associated with the action (trade or resting order). | Price at which the action occurred. |
-| `size` | Int | Quantity involved in the action. | Contracts/shares added, canceled, or traded. |
-| `flags` | Int bitmask (`0`, `128`) | Feed-specific flags (e.g., implied liquidity). | Optional filters—`128` often marks implied orders. |
-| `ts_in_delta` | Int | Microsecond delta between publisher ingest and event time. | Latency diagnostics. |
-| `sequence` | Int | Monotonic sequence number assigned by the feed. | Ensures deterministic replay order. |
-| `bid_px_00` | Decimal | Best bid price after the event. | Top-of-book bid for immediate execution. |
-| `ask_px_00` | Decimal | Best ask price after the event. | Top-of-book ask for immediate execution. |
-| `bid_sz_00` | Int | Total size resting at `bid_px_00`. | How much liquidity is available to buy at that price. |
-| `ask_sz_00` | Int | Total size resting at `ask_px_00`. | How much liquidity is available to sell at that price. |
-| `bid_ct_00` | Int | Number of distinct orders at the best bid. | Depth granularity—shows how distributed the liquidity is. |
-| `ask_ct_00` | Int | Number of distinct orders at the best ask. | Helps infer queue length and resiliency. |
-| `symbol` | String (`NQU5`, `NQZ5`) | Human-readable instrument code (Sep/Dec 2025 Nasdaq-100 futures). | Quick instrument identification when browsing CSVs. |
-| `date` | Date (`YYYY-MM-DD`) | Trading session date. | Partitioning and quick filtering without parsing timestamps. |
-
-## 4. How the columns work together
-
-1. **Event intent** – `action`, `side`, `price`, `size` tell you what just happened.
-2. **Book state** – `bid_*` and `ask_*` show how the best quotes look immediately after the event finishes.
-3. **Ordering & timing** – `ts_event`, `ts_in_delta`, `sequence` let you recreate the timeline faithfully.
-4. **Identity** – `instrument_id` + `symbol` ensures you know which instrument changed, even if you join across datasets.
-
-## 5. Reading a full row step-by-step
-
-Take the second row of the sample:
-
-```2:3:data/realdatasample.csv
-2025-08-29 13:29:59.999832391+00:00,1,1,42008487,C,B,0,23652.0,1,128,13182,194342359,23651.75,23652.5,4,5,4,5,NQU5,2025-08-29
-```
-
-1. **Action** – `C` (Cancel) on the bid side at 23,652 removing 1 contract (likely clearing residual size after the trade).
-2. **Flags** – `128` indicates this cancel touched an implied order (per CME coding).
-3. **Sequence** – `194342359`, just after the prior trade, confirming chronological order.
-4. **Resulting book** – Bid price drops to 23,651.75 with 4 contracts; ask stays 23,652.50 with 5. The cancel depleted the rest of the top-level bid, so the next bid becomes visible.
-
-By repeating this reasoning down the file you can replay how liquidity evolved second-by-second.
-
-## 6. Mental model: table vs. raw book
-
-- The CSV is **not** a table of aggregated bars. Every row is an *event* plus the *snapshot right after it*.
-- Think of it as “deltas + state”:
-  1. Deltas: `action`, `side`, `price`, `size`.
-  2. State: `bid_*`, `ask_*`.
-  3. Ordering: `ts_event`, `sequence`.
-
-Armed with these three pieces, you can reconstruct spreads, mid-prices, liquidity consumption, and even derive candles if needed.
-
-## 7. Recap checklist
-
-- ✅ Know that `mbp_1` ≈ “Level-1 order-book events.”
-- ✅ One row = one market event + resulting top-of-book snapshot.
-- ✅ Columns fall into four buckets: metadata, event details, book snapshot, identifiers.
-- ✅ You can interpret every column in the sample CSV and explain what changed between any two events.
-
-Once you’re comfortable with this schema, you can confidently ingest larger `mbp_1` shards, simulate executions, or convert the stream into higher-level indicators such as spreads, liquidity imbalance, and micro-price. The same principles extend to deeper schemas (`mbp_10`, `mbo`) where additional price levels or per-order details are provided.
