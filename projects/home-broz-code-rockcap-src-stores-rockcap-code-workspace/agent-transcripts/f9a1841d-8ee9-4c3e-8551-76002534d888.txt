- **Why you want them**:
  - **They’re the real source of truth** for your system (activation → menu → handlers → workflows).
  - **Composable + referenceable**: you can say “use `@broz/mode.build`” and get consistent behavior across sessions.
  - **Auditable**: a rule is just a file you can read/review/version like code.

#### Commands (`.cursor/commands/.../*.md`)
- **What they are**: “Clickable / runnable entrypoints” from the Cursor Commands UI. Think of them as **macros** that paste a well-formed prompt into chat (often referencing rules).
- **Why you want them**:
  - **Fast + consistent start**: you don’t have to remember exact `@broz/...` references or wording.
  - **Forces the menu**: your requirement “every mode invocation starts with a menu” is easiest to enforce via commands (the command always begins with “load mode rule → run activation → show menu → pick handler”).
  - **Reduces operator error**: one click to start “BUILD” the right way, instead of ad‑hoc prompting.

## Commands vs rules (and why both)
- **Commands** are the *entrypoints* you invoke. They should:
  - route into the correct mode
  - force the mode menu
  - then execute the selected handler/workflow
- **Rules** are the *behavior contracts* (activation/menu/handlers/workflows). Keeping them in rules makes the “system logic” referenceable and auditable, instead of hiding it inside command prose.
- **Manual vs alwaysApply**:
  - `broz/core.mdc` should be **alwaysApply: true** because it’s tiny and prevents drift.
  - mode rules stay **manual** so only the active mode’s logic is loaded.

## `plans/context.yaml` schema (strict BUILD gating)
This YAML is the state machine. BUILD can only execute `tickets.current` when it points to an existing file.

  research_path: "docs/research/RESEARCH-2025-12-12-some-topic.md"    # optional
  docs_path: "docs/<tbd>.md"                                          # optional

## Mode Menus & Workflows (Detailed)
Every mode invocation **always** presents its menu first.

### MENU Mode (Global Router)
**Menu:**
1. `plan`: **PLAN Mode** (Manage epics & tickets)
2. `build`: **BUILD Mode** (Implement active ticket)
3. `task`: **TASK Mode** (Execute one-off task)
4. `research`: **RESEARCH Mode** (Explore & investigate)
5. `docs`: **DOCS Mode** (Manage documentation)

**Handlers/Workflows:**
- All handlers simply activate the target mode’s rule (`@broz/mode.plan`, etc.) and invoke its menu.

### PLAN Mode
**Menu:**
1. `new_epic`: Create a new Epic & Plan
2. `edit_epic`: Modify/Update an existing Epic Plan
3. `shard`: Shard Plan into Tickets (in current Epic)
4. `add_ticket`: Add single Ticket to existing Epic

**Handlers/Workflows:**
- `workflow.new_epic`: Scaffolds `plans/epics/EPIC-####-name/` + `PLAN.md` from template → updates `context.yaml`.
- `workflow.edit_epic`: Lists epics → user selects → loads `PLAN.md` → updates `context.yaml`.
- `workflow.shard`: Reads active `PLAN.md` → parses tasks → generates `tickets/TICKET-####-name.md` files → updates `tickets.next`.
- `workflow.add_ticket`: prompts for ticket details → writes `TICKET-####.md` → updates `tickets.next`.

### BUILD Mode (Strict)
**Menu:**
1. `continue`: Continue current ticket (from `context.yaml`)
2. `start_next`: Select & start a ticket from `tickets.next`
3. `ad_hoc`: (Redirects to PLAN `add_ticket` or TASK mode)

**Handlers/Workflows:**
- `workflow.continue`: Verifies `tickets.current` exists → reads it → reads context → prompts for next step.
- `workflow.start_next`: Lists `tickets.next` → user picks one → moves it to `tickets.current` (updates YAML) → reads ticket → starts build.
- *Constraint*: If `tickets.next` is empty and user wants new work, handler aborts and suggests switching to PLAN.

### TASK Mode
**Menu:**
1. `new_task`: Start a new standalone task
2. `resume_task`: Resume a recent task log

**Handlers/Workflows:**
- `workflow.new_task`: Creates `plans/tasks/TASK-YYYY-MM-DD-slug.md` → updates `context.yaml` → starts execution logging.
- `workflow.resume_task`: Lists recent task files → user selects → updates `context.yaml` → appends to log.

### RESEARCH Mode
**Menu:**
1. `new_research`: Start new Research investigation
2. `resume_research`: Resume existing Research note
3. `promote`: Promote findings to Plan/Ticket

**Handlers/Workflows:**
- `workflow.new_research`: Creates `docs/research/RESEARCH-YYYY-MM-DD-slug.md` (from template) → updates `context.yaml`.
- `workflow.resume_research`: Lists `docs/research/` → selects file → updates `context.yaml`.
- `workflow.promote`: Reads research findings → triggers `workflow.add_ticket` (in PLAN mode) or suggests `workflow.new_epic`.

### DOCS Mode
**Menu:**
1. `create_doc`: Create new doc from template
2. `audit_comments`: Audit code comments/JSDoc against standards
3. `extract_wiki`: Extract JSDoc to wiki-style docs (scaffold)

**Handlers/Workflows:**
- `workflow.create_doc`: Prompts for type (howto/design/decision) → copies `docs/templates/doc.template.md` → opens for write.
- `workflow.audit_comments`: Scans codebase for missing/bad comments → generates a todo list of fixes.
- `workflow.extract_wiki`: (Placeholder) Runs script to parse JSDoc → generates markdown files in `docs/wiki/`.

## Why these choices
- **`broz/` namespace + dedicated subdirs**: makes the system portable and clearly separated from BMAD.
- **Menus everywhere**: you get consistent activation and “handler selection” behavior; less ambiguity and fewer accidental side-paths.
- **BUILD strictness via context.yaml**: forces the discipline you want: you can’t build something that wasn’t planned (or at least written as an existing ticket).
- **Separate `plans/` vs `docs/`**: keeps execution artifacts lean while letting docs/research mature into a doc site later.
