### How validation would fail (examples)

Validation fails whenever the ticket can’t be safely handed to `build/continue` **without guessing**. Concretely, failure happens if any of these are true:

- **Missing required structure**: e.g. no `## Acceptance Criteria`, no `## Tasks`, no `## Tests` (with both `### E2E Tests` + `### UNIT TESTS`), no `Status:` line, no front-matter/tags.
- **Broken AC ↔ Tasks traceability**:
  - A top-level task is missing `(AC: AC-#...)`, or
  - An `AC-#` exists that no top-level task references.
- **Open Questions remain**: at least one checkbox in `## Questions` is still unchecked after the dialogue loop (meaning stakeholder input is still needed).
- **Tests not sufficiently specified** (after attempting to extend): test cases are still vague (no clear expected outcome, or missing the “how” bullets), or key tests can’t be described due to missing inputs/expected outputs (which should become open Questions).
- **Front-matter/taxonomy issues**: missing `plan/ticket` tag, invalid tags vs taxonomy (and unresolved via Questions), or `facets.repo.path` doesn’t match the ticket path.
- **Status conflicts**: ticket `Status:` indicates it’s not ready for planning handoff (e.g. already `In Progress` / `Done`) and the metadata doesn’t match, without an explicit decision captured in Questions.
