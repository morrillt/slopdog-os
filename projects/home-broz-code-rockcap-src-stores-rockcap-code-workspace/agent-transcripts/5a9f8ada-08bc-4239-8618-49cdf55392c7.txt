# Step SL 12.16 - Stepped Stop Loss Strategy

## Overview

**Step SL 12.16** is a stepped stop-loss trading strategy that does not use ORB (Opening Range Breakout) or ATR indicators. This strategy focuses on directional trading with profit-protecting stop loss adjustments.

This version (12.16) is a fork of strategy 12.10.1 with three critical bug fixes implemented on December 16, 2025. The original 12.10.1 baseline is preserved for comparison and A/B testing purposes.

## Key Features

- **Directional Trading**: Requires direction change after both SL and TP hits (not just SL)
- **Stepped Stop Loss**: Automatically adjusts stop loss to lock in profits as trade moves favorably
- **Variable Start Price**: Start price shifts at 9:35 AM ET to the 9:35:00 candle's open price
- **Force Close Logic**: Trades are force-closed at 9:35 AM for session reset
- **Cutoff Time**: Configurable cutoff time (default: 09:45) to prevent late-day entries

## Strategy Behavior

### Entry Logic

1. **Trigger-Based Entry**: Price must cross above/below start price by `triggerPts` amount
2. **Alternating Direction**: After an SL or TP hit, the next trade must be in the opposite direction
3. **9:35 Reset**: At 9:35 AM, the start price resets and round-trip counter resets

### Exit Logic

1. **Take Profit (TP)**: Calculated from **trigger/entry price** + `profitTargetPts` (not start price)
2. **Stop Loss (SL)**: 
   - Initial SL calculated from trigger price ± `stopLossPts`
   - **Direction Validation**: SL only triggers when price moves in the **opposite direction** to the trade
   - **Stepped SL**: As profit increases, SL adjusts upward (longs) or downward (shorts) to lock in gains
3. **Force Close**: Trades close at 9:35 AM or cutoff time

### Stepped Stop Loss Configuration

The strategy supports profit-threshold-based stop loss adjustments:

```typescript
stopLossByProfitThreshold: {
  "1": 0.5,   // At 1pt profit, lock 0.5pts
  "2": 1,     // At 2pts profit, lock 1pt
  "5": 2,     // At 5pts profit, lock 2pts
  "10": 5,    // At 10pts profit, lock 5pts
}
```

## Version 12.16.1 Release Notes

**Release Date**: December 17, 2025  
**Forked From**: Strategy 12.10.1  
**Baseline Commit**: `58baca0` (before bug fixes)

### What Changed

This release includes three critical bug fixes that improve strategy correctness and reliability:

#### Bug Fix 1: Stop Loss Direction Validation ✅

**Problem**: Stop loss was not fully enforcing the requirement that trades must be in the opposite direction. In some edge cases, stop loss could trigger incorrectly when price moved in the same direction as the trade.

**Fix**: Enhanced stop loss validation to strictly enforce that stop loss only triggers when price moves in the **opposite direction** to the trade direction.

**Impact**: Prevents premature trade exits and ensures stop loss logic aligns with strategy intent.

**Validation**: 
- Test cases verify incorrect-direction stops do NOT close trades
- Test cases verify correct-direction stops DO close trades

#### Bug Fix 2: Take Profit Based on Trigger Price ✅

**Problem**: Take profit (TP) was incorrectly calculated from the start price instead of the actual trigger/entry price. This caused TP levels to be offset incorrectly, especially after the 9:35 start price shift.

**Fix**: Changed TP calculation to use the **trigger price** (entry basis) instead of start price:
- **Long TP**: `triggerPrice + profitTargetPts`
- **Short TP**: `triggerPrice - profitTargetPts`

**Impact**: TP levels now correctly reflect the intended profit target relative to entry, not relative to the start price.

**Validation**:
- Test cases verify TP is calculated from trigger price
- Test cases verify old behavior (start-price TP) would fail

#### Bug Fix 3: Time Interval Respect ✅

**Problem**: Time interval configuration was not being properly respected. The strategy could treat "minutes" as candle counts rather than actual time intervals, causing incorrect behavior with 1-second candle data.

**Fix**: Updated interval logic to use **timestamp-based calculations** (e.g., 5 minutes = 300 seconds) instead of candle counts.

**Impact**: Ensures time-based configurations work correctly regardless of candle granularity (1-second, 1-minute, etc.).

**Validation**:
- Test cases verify interval logic uses timestamps (N minutes = N*60 seconds)
- Test cases verify no trades occur before configured interval boundary

- **Wrong profit targets**: TP levels not matching intended strategy behavior

# Publishing New Strategies - UI Integration Guide

**When to use this guide**: Every time you publish a new strategy and want it to appear in the UI with full functionality.

This guide documents the **complete checklist** of UI integration steps required when adding a new strategy to the codebase. Missing any step will result in the strategy not working correctly in the UI.

---

## Quick Checklist

When publishing a new strategy, you must:

1. ✅ **Set production flag** (`production: true`)
2. ✅ **Add to strategy registry** (`src/lib/backtest/strategies/index.ts`)
3. ✅ **Update default strategy** in store (if making it the new default)
4. ✅ **Add to stepped SL conditions** (if strategy supports stepped SL)
5. ✅ **Add to line visibility toggles** (if strategy uses 9:35 start price shift)
6. ✅ **Test stepped SL config input** (if applicable)
7. ✅ **Test stepped SL line rendering** (if applicable)

---

## Step-by-Step Guide

### 1. Create Strategy File

Create your strategy file in `src/lib/backtest/strategies/` following the existing pattern:

```typescript
export const myNewStrategy: Strategy = {
  id: "my-new-strategy",
  name: "My New Strategy",
  description: "Short description for dropdown", // Keep this SHORT!
  production: true, // ✅ Set to true to show in UI
  run: runMyNewStrategy,
};
```

**Important**: Keep the `description` field **short** (under 60 characters). It appears in the dropdown and long descriptions make the UI cluttered.

### 2. Add to Strategy Registry

Import and add to the `strategies` array in `src/lib/backtest/strategies/index.ts`:

```typescript
import { myNewStrategy } from "./my-new-strategy";

const strategies: Strategy[] = [
  // ... existing strategies
  myNewStrategy, // Add here
];
```

### 3. Set Production Flag

**Critical**: Only strategies with `production: true` appear in the UI dropdown.

- **New strategy**: Set `production: true`
- **Old strategies**: Set `production: false` if you want to hide them (they'll still be available in scripts)

**Example**: When publishing Step SL 12.16, we set:
- `strategy12dot16.production = true` ✅ (visible in UI)
- `strategy12dot10dot1.production = false` ❌ (hidden from UI, but available in scripts)
- `atr-trailing-stop.production = false` ❌ (hidden from UI)

### 4. Update Default Strategy (Optional)

```typescript
export const backtestState = proxy<BacktestState>({

  selectedStrategyId: "my-new-strategy",
  // ...
});
```

## Common Mistakes

### ❌ Mistake 1: Forgetting Production Flag

**Symptom**: Strategy doesn't appear in dropdown  
**Fix**: Set `production: true` in strategy definition

### ❌ Mistake 2: Long Description

**Symptom**: Dropdown is hard to read, UI looks cluttered  
**Fix**: Keep description under 60 characters

### ❌ Mistake 3: Missing Stepped SL Conditions

**Symptom**: Stepped SL config input doesn't appear, lines don't render  
**Fix**: Add strategy ID to all three conditions (config input, line rendering, line toggles)

### ❌ Mistake 4: Not Regenerating on Config Change

**Symptom**: Config changes don't affect trades until manual refresh  
**Fix**: Add `actions.generateAlgoTradesForDay()` in onChange handlers

### ❌ Mistake 5: Multiple Strategies Published

**Symptom**: Multiple strategies appear in dropdown when only one should  
**Fix**: Set old strategies to `production: false`

## Notes

- **Production Flag**: This is an opt-in flag. Strategies default to `production: true` if not specified, but it's better to be explicit.
- **Scripts vs UI**: Scripts use `getStrategy(id)` which doesn't filter by production flag. Only UI uses `getStrategies(true)` which filters.
- **Backward Compatibility**: Setting old strategies to `production: false` doesn't break scripts - they can still reference them by ID.
